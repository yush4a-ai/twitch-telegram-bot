# TwitchSignalBot — Roadmap развития

Статус: утверждён пользователем 2026-09-30.

Исходная точка: `6074744` (`main`) — live preview отправляется как Telegram Animation, цикл ограничен 24 секундами с защитой размера.

## Принципы

- TwitchSignalBot — отдельный проект. Не смешивать с CigilBot и Media.
- Новые функции сначала проверяются в staging через `@TwitchSignalTestbot`.
- Production получает только отдельно принятую версию.
- Для крупных этапов порядок один: спецификация → implementation plan → реализация → тесты → staging → ручная приёмка → production.
- Не считать коммит или локальные тесты выпуском.
- Не принимать технические догадки за факты: всё спорное подтверждать кодом, тестом, логами или документацией.
- Не усложнять архитектуру заранее без измеренной необходимости.

## Этапы

### R0 — Audit & Baseline
Зафиксировать реальное состояние кода, инфраструктуры, данных, тестов, документации и рисков. Результат — доказательная baseline-карта и точный scope следующего этапа.

### R1 — Безопасная схема разработки и staging
Закрепить ветки/окружения, изоляцию секретов и баз, воспроизводимый deploy, runbook и rollback. Staging не должен влиять на production.

### R2 — Owner Admin Panel v1
Read-only панель владельца:
- здоровье Telegram/Twitch/preview отдельно;
- аудитория и сообщества;
- текущие эфиры и preview;
- ошибки и очередь;
- базовая нагрузка/ресурсы.
Опасные действия пока не добавлять.

### R3 — Коммерческая техническая основа
Подготовить архитектуру к росту без преждевременных микросервисов:
- спроектировать миграцию данных при необходимости;
- отделить общие данные эфира от per-destination состояния;
- durable queue для отправки;
- ограниченная тяжёлая preview-обработка;
- нагрузочные сценарии и измерения.
Решение о PostgreSQL принимать по результатам аудита и требований следующего этапа.

### R4 — Streamer Plus без реальных платежей
- entitlement/access model вместо одного `premium=true`;
- кабинет стримера;
- безопасный конструктор live-поста;
- измеримая статистика пользы бота;
- ручная/тестовая выдача доступа.

### R5 — Платежи
После отдельной проверки провайдеров, правил Telegram и юридической возможности:
- один основной платёжный провайдер для пилота;
- подтверждение оплаты только server-side;
- idempotency;
- срок доступа, возвраты, отмены;
- финансовый audit log;
- никаких ложных “успешных оплат” по redirect-странице.

### R6 — Закрытый Streamer Plus pilot
5–10 приглашённых стримеров:
- staging acceptance;
- ограниченный production rollout;
- наблюдение за расходами, ошибками, использованием;
- отдельное разрешение перед каждой коммерческой ступенью.

### R7 — Telegram Mini App + Viewer Plus
- единый кабинет, не отдельный продукт;
- серверная валидация Telegram init data;
- smart alerts по категории/названию;
- digest пропущенного;
- отдельный viewer pilot.

### R8 — Growth / SEO / referrals
- attribution от deep-link до оплаты;
- публичный сайт;
- SEO-страницы;
- реферальные механики с защитой от накрутки;
- оценка источников по активациям и оплатам, а не только по /start.

### R9 — Подтверждение масштаба 20–40k
Не обещать масштаб без измерений:
- синтетические профили нагрузки;
- fan-out latency;
- queue depth;
- DB latency;
- CPU/RAM/disk;
- preview concurrency;
- recovery;
- payment idempotency;
- runbook и backup/restore drill.

## Границы продукта

### Free
- личное отслеживание стримеров;
- базовые go-live уведомления;
- базовые публикации в сообществах;
- существующие отчёты и полезные функции не отнимать внезапно.

### Streamer Plus
Кандидаты:
- live preview;
- расширенное оформление;
- дополнительные контролируемые кнопки;
- несколько сообществ;
- измеримая статистика.

### Viewer Plus
Кандидаты:
- правила по игре/категории;
- title/keyword filters;
- исключения;
- digest;
- дополнительные preview-возможности только после проверки стоимости и правил.

## Открытые решения до коммерческого запуска

- платёжный провайдер;
- получатель платежей и требования к возрасту/статусу;
- цены и квоты;
- правила продажи цифровых функций внутри Telegram;
- допустимость коммерческой продажи live preview с учётом правил Twitch;
- бюджет инфраструктуры;
- сроки хранения данных.

Эти вопросы не блокируют R0–R2, но должны быть закрыты до соответствующего коммерческого этапа.
