# R8 — Attribution, referrals и SEO prototype: design

Дата: 2026-10-01. Основание: утверждённый `docs/ROADMAP.md`, инженерная приёмка R0–R7, owner-approved дополнение `docs/workflows/2026-10-01-r8-seo-design-remotion.md` и уточнение качества органического поиска `docs/workflows/2026-10-01-r8-competitive-seo.md`, прочитанные на контрольной точке R8. Реализация и публикация только на закреплённом Railway staging с `@TwitchSignalTestbot`; production, реальные платежи, награды и внешняя индексация не входят в этот этап.

## Цель и проверяемый результат

Проследить в тестовом контуре переход конкретного пользователя от безопасного Telegram deep link к первому подключению Twitch-канала и последующему тестовому Plus entitlement. Дать обычному пользователю реферальную ссылку без ID в URL, владельцу — только агрегированную воронку по источникам. Подготовить узнаваемый многостраничный SEO-прототип с двумя исходными визуальными направлениями и отдельное локальное демонстрационное видео в горизонтальной и вертикальной версиях. На staging страницы явно закрыты от индексации. События измеряют действия в боте, не просмотры сайта, клики без `/start`, доход или количество реальных продаж.

## Подход и границы данных

- Выбран первый допустимый touch: `src_site` для прототипа сайта или `ref_<opaque>` для выданного ботом реферального кода. Telegram документирует private `/start` parameter до 64 символов; код ограничивается ASCII URL-safe алфавитом и этой длиной ([Telegram Bot Features](https://core.telegram.org/bots/features#deep-linking)). Другие/неизвестные параметры сохраняют прежний `/start` flow, без attribution. Существующие `track_` и `link_` обрабатываются раньше и не меняют семантику.
- `growth_referral_codes` хранит единственный случайный 12-символьный base64url код на Telegram user ID. Код создаётся по `/invite` только в личном чате на pinned staging, возвращается тому же пользователю и не содержит ID. Не выдаются деньги, скидки, приоритеты и права Plus. Код можно открыть повторно, но новый код для того же referrer не выпускается. Самореферал, несуществующий код, группа/канал, несовпадение `from_user.id` и private `chat.id` и повторный touch не создают referral credit. Ответ `/start` остаётся обычным, чтобы не делать oracle по кодам.
- `growth_attributions` содержит только `(telegram_user_id, source_kind, source_code, referrer_user_id|null, first_seen_at, activated_at|null)`. Запись создаётся только для ранее не активированного private пользователя без `tracked_channels`, один раз на ID; дальнейшие `/start` не перезаписывают источник. Для `src_site` допустим ровно зарегистрированный статический код `site`, без произвольных UTM и user IDs. Первый успешный `add_channel`/`add_channel_with_limit` ставит `activated_at` в той же DB транзакции, поэтому duplicate/limit/Twitch error не считаются активацией. Удаление канала не стирает историческое событие.
- Plus conversion считается агрегатно из существующих `entitlement_grants` после `activated_at`: `viewer_plus` по Telegram user ID и `streamer_plus` по текущей `streamer_identities` связи. Считать уникального пользователя один раз, включая позже отозванный/истёкший тестовый grant, как **ever test entitlement**, а не активный платёж или доход. При смене Twitch identity историческая streamer conversion может быть не видна через текущую связь; эта граница отражается в отчёте. Личные ID и реферальные коды не возвращаются в owner dashboard.
- Публичный site не ставит cookies, пиксели и сторонние скрипты; нет IP/UA логики attribution. Если Telegram `/start` не пришёл, посещение сайта не считается. Тестовые данные staging не копируются из production.

## Интерфейсы и изоляция

- Флаг R8 включается локально и только при точном pinned Railway staging ID; production Railway отвергает функциональность. В личном testbot `/invite` выдаёт ссылку `https://t.me/TwitchSignalTestbot?start=ref_<code>`. Общие bot commands и групповые меню не получают `/admin` или управленческих ссылок. Attribution handler принимает только private Telegram actor из проверенного update, никогда ID из URL/JSON.
- Staging live-пост с кнопкой «Подключить уведомления» должен направлять к testbot, а не к production username: `build_track_deep_link` получает проверенный bot username из runtime; локальные вызовы без параметра сохраняют прежнее значение для совместимости. Это отдельная регрессия staging boundary.
- Сайт монтируется на `/site`, `/site/for-viewers`, `/site/for-streamers`, `/site/help` только на staging. Серверный HTML/CSS содержит уникальные `<title>`/description/H1, понятную навигацию и внутренние ссылки, breadcrumb на внутренних страницах, правдивое описание Free/тестового Plus и ссылку на testbot `?start=src_site`. Canonical на staging указывает на тот же staging URL и служит только проверкой шаблона; финальный домен не выбран. Никаких цен, реальной оплаты, гарантий масштаба, отзывов, рейтингов, выдуманных стримеров, персональных данных или обещаний SEO-позиций. Допустимая JSON-LD разметка описывает только видимый сайт и его страницы, без фиктивных offers/reviews. `/site/*` получает HTTP и HTML `noindex, nofollow`; `/robots.txt` **не блокирует эти страницы**, чтобы поисковый робот мог увидеть `noindex`. Google прямо указывает, что Disallow скрывает от робота сам noindex и URL всё ещё может появиться в выдаче ([документация](https://developers.google.com/search/docs/crawling-indexing/block-indexing)). Серверная авторизация продолжает защищать личные поверхности. Sitemap и Search Console/Яндекс submission откладываются до публичного решения. На staging нет cookies, пикселей или тяжёлого обязательного autoplay.
- Read-only owner dashboard добавляет агрегатную таблицу `source → touched → activated → ever test Plus` (кампания site и referrals как тип, без кода/referrer ID). Те же данные идут через существующий `/admin/api/snapshot`, с прежней owner auth; обычный пользователь и прямой URL не получают их. Ошибка growth SQL помечает блок недоступным, не ломая health snapshot.

## Визуальное направление и содержание сайта

- Отдельный `docs/design/public-site.md` хранит surface brief, карту четырёх страниц, исследованные темы-гипотезы без выдуманной частотности, два лёгких варианта первого экрана и причину обратимого выбора. Варианты отличаются композицией: «Сигнал эфира» строит образ поступающего сигнала и заметного Telegram-поста; «Из эфира в Telegram» показывает путь Twitch → пост → зритель. Для прототипов можно использовать доступную генерацию изображений, но факт её использования фиксируется честно. Весь сайт на существующем aiohttp/HTML, без перевода бота на React и без копирования admin UI.
- Design read: публичный продуктовый сайт для зрителей и стримеров, с ясной технической атмосферой, выразительной кириллической типографикой и одним демонстрационным элементом. Навигация ведёт к задачам «Я зритель», «Я стример», «Как это работает». Реальные возможности объясняются на страницах, демо-пост и эфир явно маркируются как синтетический пример. UI проверяется при 360/390/768/1440 px, клавиатурой, с контрастом и `prefers-reduced-motion`; макет не зависит от видео.
- SEO-checklist разделяет техническую готовность шаблона и будущий публичный запуск Google/Яндекс. Контентные гипотезы «уведомления Twitch в Telegram», «пост о начале эфира в канале», «оповещения по игре» проверяются по доступным публичным источникам без объявления объёма спроса. Нельзя создавать множество тонких страниц или утверждать фактический поисковый трафик staging.
- До окончательной карты страниц проводится датированный небольшой анализ прямых альтернатив по их собственным страницам: hosted Telegram сервисы отделяются от self-hosted кода и Discord; отсутствие опубликованного описания не объявляется отсутствием функции. Около 20–30 запросов остаются гипотезами, объединёнными по 6–8 задачам, без выдуманного спроса. Дополнительная страница появляется только при отдельной полезной задаче, а не из-за варианта написания запроса. Нельзя обещать первое место или использовать манипулятивные SEO/CRO приёмы. Начальный рынок — русскоязычный контент; выбор страны, домена, бренда, публичного запуска и индексирования остаётся за владельцем.
- Проверка скорости сохраняет фиксированные условия лабораторного прогона и различает их от реальных Core Web Vitals. После будущего запуска измерять запросы/страницы в Google Search Console и Яндекс Вебмастере только с разрешёнными подтверждёнными аккаунтами; до него подготовить checklist и шаблон недельного отчёта без фоновой автоматизации. Воронка `src_site` измеряет старт бота по этой ссылке, не органический поисковый запрос.
- Домен, публичное название и страна запуска не выбираются автоматически. [Twitch Trademark Guidelines](https://www.twitch.tv/p/nl-nl/legal/trademark/) запрещают использование Twitch Brand Assets в доменном имени и названии продукта без разрешения; действующее имя бота не переименовывается этим R8 пакетом, но остаётся вопросом перед публичным запуском. Опубликованные тарифы и доступность домена требуют отдельной проверки при покупке; R8 ничего не покупает и не меняет BotFather/OAuth домены.

## Изолированный demo video

- `marketing/video/` — отдельный Remotion проект с закреплёнными зависимостями, без импорта в bot runtime и без тяжёлого render на Railway. Сценарий: синтетический эфир начался → Telegram-пост → живое превью как демонстрация → переход к просмотру. Это маркетинговое видео, не изменение Telegram Animation preview (6 → 12 → 18 → 24 → reset, H.264 MP4 без аудио и существующий size guard остаются).
- Сначала раскадровка и несколько кадров, затем короткий черновик в локальном Studio при доступности, после чего локальный ограниченный render 16:9 и 9:16 с poster. Используются собственные графика/текст и явно синтетические данные; без чужой музыки/роликов. Видео имеет управление запуском/паузой и лёгкую загрузку; текст сайта виден без воспроизведения. Файлы проверяются по длительности, разрешению, размеру, safe margins и отсутствию растяжения. Лицензионные условия конкретной runtime-версии проверяются до коммерческого распространения; staging preview не объявляется разрешением на публичное коммерческое использование.

## Проверка и rollout

TDD для URL-safe parser/builder и testbot username, unknown/self/group/replay referral, first-touch и атомарной activation, duplicate/limit, Plus aggregation без ID, owner auth, noindex/canonical/site link и старых `track_`/`link_`. Визуальные варианты, site и video проходят отдельную проверку по связанному дополнению. После полного suite — внешний staging backup, restore/migration на копии, чистый commit и pinned deploy guard; затем signed/admin, bot identity, site/robots и temp-DB journeys в staging. Реферальный E2E через реальный клиент и SEO indexability не объявляются проверенными по synthetic тестам. Rollback остаётся с additive schema; code-only revert не стирает исторические growth rows, а тестовые attribution данные допускают сохранение в staging.

## Самопроверка

Первый touch, activation и Plus имеют разные наблюдаемые основания. Неизвестные ссылки не создают источник и не меняют подключение. Реферальный код не даёт прав/денег и не раскрывает ID. Сайт закрыт от индексации на staging, а CTA ведёт только к testbot. Owner-only R2 auth и R7 Viewer API не расширяются; production не меняется.
