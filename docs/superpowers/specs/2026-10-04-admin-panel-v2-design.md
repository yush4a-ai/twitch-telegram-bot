# R2-Admin v2 — owner-админ-панель: design

Дата: 4 октября 2026. Статус: черновик спеки, ожидает подтверждения владельцем. Основание: [паспорт](../../design/admin-concept-2026-10-04/ADMIN-PANEL-PASSPORT.md), [концепт-макет](../../design/admin-concept-2026-10-04/CONCEPT.md), [спека R2 v1](../specs/2026-09-30-r2-owner-admin-panel-design.md).

## 1. Цель и границы

Владелец открывает браузерную панель и за один сеанс решает три задачи: понять, что происходит с ботом; найти конкретного человека и увидеть его права, лимиты и историю; выдать, продлить или отозвать доступ, не заходя в CLI.

Что сохраняется без изменений: строгая авторизация владельца (подпись Telegram, свежесть, owner id, аварийный ключ, серверные сессии), отсутствие моков на живых маршрутах, отсутствие кнопок деплоя и управления production, выключенные платежи, CSP без внешних CDN.

Что появляется впервые: имена и username пользователей (только в панели владельца), отметка последней активности, чтение журнала прав, выдача/продление/отзыв из веба.

## 2. Что меняется в существующих документах

- `PRODUCT.md`: снимается утверждение «R2 owner panel только читает данные» и запрет на персональные имена в снапшоте; вместо них — «панель владельца читает состояние и управляет ручными доступами; имена видны только владельцу».
- `DESIGN.md`: визуальная система заменяется с navy на графит из макета (см. раздел 11).
- Спека R2 v1 остаётся историческим документом: авторизация, гейтинг по окружению, security-заголовки и требования к честным состояниям переносятся в эту спеку без изменений.

## 3. Информационная архитектура

Разделы: **Обзор**, **Пользователи**, **Доступы**, **Рост**, **Система**, **Оплаты**.

Маршруты — хеш внутри единственной страницы `/admin`, чтобы не добавлять серверные пути и не расширять область cookie:

| Адрес | Экран |
| --- | --- |
| `/admin#/overview` | Обзор (по умолчанию) |
| `/admin#/users` | Пользователи: поиск и список |
| `/admin#/users/<telegram_id>` | Карточка пользователя |
| `/admin#/access` | Доступы: вкладки «Действующие» и «История» |
| `/admin#/system` | Система |
| `/admin#/growth` | Рост (честная заглушка) |
| `/admin#/payments` | Оплаты (заглушка) |

Правила навигации:

- Экран человека имеет собственный адрес; возврат к списку сохраняет прежний запрос, фильтр и позицию прокрутки в пределах сеанса (`sessionStorage`).
- Выдача и продление открываются поверх карточки диалогом; отзыв — отдельным подтверждением с явным составом прав после отзыва.
- Поиск доступен из любого раздела. `Ctrl/Cmd+K` только дублирует видимую кнопку.
- Окружение в шапке подписано словом (`STAGING` / `LOCAL`); переключения окружений в панели нет.

## 4. Оболочка

- Десктоп: постоянный сайдбар 200–216 px, рабочая область до 1440 px, поля 32 px, промежутки 24 px.
- Мобильный (<768 px): нижняя навигация «Обзор / Люди / Доступы / Ещё»; в «Ещё» — Рост, Система, Оплаты, профиль. Заголовок раздела остаётся полным.
- Шапка: имя продукта, метка окружения, время последнего успешного обновления, «Обновить», «Выйти».
- Один и тот же набор компонентов на всех ширинах; отдельной «мобильной версии» нет.

## 5. Экраны

### 5.1 Обзор

Порядок: заголовок и свежесть данных → строка здоровья («Система работает» / «Есть задержки» / «Не удалось проверить» с действием «Проверить») → одна группа показателей (всего пользователей, активны сегодня, новые за 7 дней, активный Plus, отправлено за 24 часа) → «Требует внимания» (до трёх проблем по влиянию на людей) → график активности за 7 дней → быстрые действия («Найти пользователя» — основное, «Выдать доступ» — вторичное).

Правила: при серьёзном отказе блок внимания поднимается выше показателей; при исправной системе достаточно строки «Нет открытых проблем». Каждый показатель несёт собственный период. Сравнение с прошлым периодом — только при одинаковой длине и полноте данных; иначе сравнение не показывается. Если история недоступна, вместо графика — «Недостаточно данных».

### 5.2 Пользователи

Крупное поле поиска, затем сегменты «Все / Plus / Активны сегодня»; расширенные фильтры (план, истекающий срок) — за кнопкой «Фильтры».

Поиск принимает `@username`, username без `@`, числовой Telegram ID и Twitch login без учёта регистра. Точное совпадение ID — первым. Одинаковые имена различаются по Telegram ID. Результаты — после короткой паузы ввода; Enter запускает сразу; пустая строка возвращает список без фильтра. Список — постранично.

Строка результата: аватар (инициал), имя, `@username`, Twitch при совпадении, тариф, последняя активность. Точные даты и лимиты — внутри карточки.

Состояния: «Пользователь не найден. Проверьте Telegram ID или имя» отличается от «Не удалось загрузить пользователей» с кнопкой «Повторить». После возврата из карточки фокус остаётся на выбранной строке.

### 5.3 Карточка пользователя

Сверху: имя, `@username`, копируемый Telegram ID. Далее карточка текущих прав: тариф, точный срок, происхождение (ручная выдача / оплата / тест), для Streamer Plus — строка «Viewer Plus включён». Основное действие «Изменить доступ», рядом «История».

Ниже две группы: **Аккаунты** (Telegram, Twitch, канал-источник при наличии) и **Активность** (последнее действие и время). Затем использование лимитов: отслеживаемые стримеры, выбранные видеопревью, подключённые Telegram-каналы. Для Free — «Видео доступно с Plus» вместо доступного лимита. Число подключённых каналов показывается без выдуманного общего лимита.

Лента событий: действие, время, исполнитель, результат; по умолчанию последние пять, полная история — в разделе «Доступы».

Состояния-заглушки: «Источник не определён», «Не подключён», «Нет данных» (не «Никогда»).

### 5.4 Выдача, продление, отзыв

Диалог 520 px на десктопе, отдельный экран на телефоне. Состав: получатель и ID → тариф → срок → причина → комментарий (необязательный) → итог → действие. Из карточки получатель уже заполнен и скрыто не меняется; из глобальной кнопки сначала обязательный поиск и выбор человека.

Тариф: Viewer Plus или Streamer Plus; при Streamer сразу видно «Включает Viewer Plus». Срок: точная дата и время либо число дней; интерфейс показывает итоговый момент в МСК; прошедшая дата и пустое значение запрещены; бессрочной выдачи по умолчанию нет.

Причина обязательна: «Компенсация», «Тестирование», «Партнёрство», «Другое»; для «Другое» — обязательное пояснение. Комментарий виден только команде и пользователю не отправляется.

Перед подтверждением — итог словами: «Выдать Streamer Plus пользователю @alex_live до 04.11.2026, 12:00 МСК. Viewer Plus включён. Списания денег не будет».

Если такое же ручное право уже действует — предлагается «Продлить» со старой и новой датой; молчаливое сокращение срока запрещено. Выдача Viewer человеку со Streamer требует явного объяснения, зачем отдельный срок; платное основание ручным не заменяется и не сокращается.

Отзыв — тихое действие ниже карточки, возвращается конкретная ручная выдача. Подтверждение показывает основание, причину и **права после отзыва**: «Streamer Plus завершится сейчас. Отдельный Viewer Plus сохранится до 20.11.2026». Если независимого Viewer нет — показывается переход на Free и затронутые функции. Настройки, подключения и данные не удаляются. Наследуемый Viewer отдельно от Streamer не выключается. Возврат оплаты, отмена оплаченного права и блокировка — отдельные операции, которых в этой версии нет.

Поведение при отправке: кнопка «Выдаём…» и защита от повторного нажатия; успех показывается только после подтверждения сервером; при потере ответа — «Результат пока не подтверждён» и проверка истории, без слепого повтора; при конфликте с параллельным изменением — «Права изменились» с новым составом и повторным подтверждением.

### 5.5 Доступы

Вкладки «Действующие» и «История». Действующие: получатель, эффективный тариф, срок, источник права; фильтры по плану, ручным выдачам и истекающим; поиск как в «Пользователях».

История: хронологическая лента событий «выдан», «продлён», «отозван», «истёк»; фильтры по человеку, действию, периоду и исполнителю; строка раскрывается в «было → стало», причину и комментарий. Истечение помечается исполнителем «Автоматически». Журнал нельзя редактировать или удалять из панели.

### 5.6 Система

Групповые строки: Telegram, Twitch, очередь уведомлений, видеопревью, база, резервная копия. У каждой — состояние, наблюдаемое время и короткое объяснение; цвет всегда сопровождается словом и знаком.

«Работает» требует свежего подтверждения конкретной функции; успешный `/healthz` не выдаётся за доставку уведомлений или готовность видео. Просроченные данные — «Данные устарели», отсутствие сигнала — «Не удалось проверить». Для очереди — размер и возраст старейшего задания. Резервная копия: отдельно дата создания и отдельно факт проверки восстановления; свежая копия не выдаётся за проверенное восстановление. Диагностические детали и идентификатор события — при раскрытии; секреты, пути и токены не показываются. Перезапуска сервисов, массового повтора рассылок и деплоя в панели нет.

### 5.7 Рост и Оплаты

«Рост»: раздел присутствует, но вместо цифр — объяснение, что сквозных данных пока нет и воронка начинается с «Открыл бота»; никаких нарисованных трендов и процентов.

«Оплаты»: «Приём платежей не подключён», будущие вкладки «Заказы / Проверка / Возвраты» и место под способы оплаты показаны неактивными с объяснением; ссылка «Выдать доступ вручную» ведёт в «Доступы» и не создаёт платёж.

## 7. Изменения схемы данных (фаза B)

Предлагаемые изменения; точные имена и порядок фиксирует план.

1. **Профиль пользователя.** Новая таблица `telegram_user_profiles(user_id PRIMARY KEY, username, first_name, last_name, language_code, updated_at)`. Заполняется при взаимодействии с ботом, показывается только в панели владельца. Старые записи наполняются по мере новых действий; разового дозаполнения из внешних источников нет.
2. **Активность.** Колонка `last_active_at` в известных личных пользователях, обновление с троттлингом (не чаще одного раза в несколько минут на человека), чтобы не нагружать горячий путь. «Активны сегодня» считается от начала суток МСК.
3. **Причина и комментарий.** Колонки `reason`, `reason_note`, `comment` в журнале прав; `reason` обязателен для ручных выдач, продлений и отзывов.
4. **Источник права.** Ручная выдача из панели пишется с `source='manual'`. Сейчас ручные выдачи и авто-триал оба используют `source='test'` (`bot/database.py:1485`, `bot/viewer_trial.py:87`), поэтому в панели они неразличимы; до этого разделения происхождение показывается как «тестовый доступ».
5. **Продление.** Новое действие `extend` в журнале и связь нового права с прежним (`previous_grant_id`), чтобы показывать «было → стало», не переписывая историю.
6. **Истечение.** Отдельной записи не требует: событие «истёк» вычисляется по сроку и помечается исполнителем «Автоматически».

Продление сохраняет принцип «право неизменяемо»: создаётся новая запись права, прежняя не редактируется. Все миграции идемпотентны и совместимы с существующей базой staging.

## 8. Write-операции: маршруты и защита

Маршруты (все требуют серверной сессии владельца, отвечают JSON, `Cache-Control: no-store`):

| Маршрут | Назначение |
| --- | --- |
| `GET /admin/api/users?q=&filter=&page=` | Поиск и список людей |
| `GET /admin/api/users/{id}` | Карточка: права, аккаунты, лимиты, активность |
| `GET /admin/api/users/{id}/history` | Лента событий человека |
| `GET /admin/api/access?state=active|history&...` | Действующие и история |
| `POST /admin/api/access/grant` | Выдача ручного права |
| `POST /admin/api/access/extend` | Продление ручного права |
| `POST /admin/api/access/revoke` | Отзыв ручного права |

Защита:

- Существующая строгая авторизация без изменений; неавторизованный запрос — 401 без данных.
- Cookie уже `SameSite=Strict`; дополнительно каждый write-запрос проверяет `Origin`/`Sec-Fetch-Site` и одноразовую метку CSRF, выданную вместе со снапшотом.
- Идемпотентность: клиент присылает `request_key`; повтор с тем же ключом возвращает прежний результат и не создаёт второе право.
- Конкурентность: запрос несёт ожидаемое состояние (`grant_id`, текущий `expires_at`); при расхождении — 409 с актуальным состоянием, операция не выполняется.
- Проверки на сервере: цель существует; тариф допустим; срок в будущем и не бессрочный по умолчанию; Viewer не сокращает Streamer; отзыв касается именно ручного права; оплаченное право через эти маршруты не отзывается.
- Каждая успешная операция пишет запись в журнал: кто, что, кому, основание, причина, комментарий, прежний и новый срок, результат. Неуспешная попытка не выглядит как состоявшаяся выдача.
- Секреты, токены и пути не попадают ни в ответы, ни в журнал, ни в UI.

## 9. Состояния и обратная связь

Единый набор для всех экранов: загрузка (скелетон в месте содержимого, без выдуманных нулей), пусто (причина и подходящее действие), ошибка (что не удалось, что сохранилось, как повторить; форма не очищается), устарело (последнее успешное время и «Обновить»; операции с правами требуют свежей перепроверки), успех (подтверждённый результат с получателем и новым сроком), нет прав (данные человека не раскрываются), сессия истекла (повторный вход с возвратом на экран; незавершённое изменение прав автоматически не отправляется).

Автообновление раз в 30 секунд сохраняется; при открытом диалоге изменения не подменяют форму.

## 10. Технические решения

- Данные для фазы A отдаются существующим `GET /admin/api/snapshot`: `AdminSnapshot` уже держит объект базы и собирает блоки. Новые блоки чтения (действующие права, история, состояния) добавляются в снапшот; правки `main.py` и `bot/oauth.py` не требуются.
- Read-only SQL для новых блоков живёт в отдельном модуле панели, чтобы не трогать `bot/database.py` в фазе A. После фазы B, когда общие файлы свободны, запросы переносятся в `Database` и модуль остаётся тонким адаптером.
- Фаза B добавляет серверные write-маршруты: они требуют передачи доступа к базе в `install_admin_routes`, то есть правок `bot/oauth.py` и `main.py` — это и есть точка синхронизации с параллельной работой.
- UI — статические HTML/CSS/JS без CDN и сборщика, как сейчас. Хеш-роутер и рендер экранов — собственный компактный JS.
- Тесты: `tests/test_admin_ui.py` фиксирует `id` элементов — при редизайне контракт обновляется вместе с кодом, без ослабления проверок; добавляются тесты на новые состояния, поиск, операции (успех, отказ, повтор с тем же `request_key`, конфликт 409, отсутствие прав) и на отсутствие утечек секретов.

## 11. Визуальная система

Палитра из макета: canvas `#171717`, surface `#242424`, raised `#2D2B31`, основной текст `#F1F1F1`, вторичный `#B9B6BF`, accent `#C7A5FF`, текст на accent `#21162F`. Семантические роли (успех, предупреждение, ошибка, неизвестность) подбираются отдельно с проверкой контраста не ниже 4.5:1 для обычного текста и попадают в `DESIGN.md` как токены.

Радиусы: карточки 20 px, смысловые группы до 24 px, кнопки 12 px. Отступы 4/8/12/16/24/32/48. Типографика: заголовок экрана 30–32 px, секции 18–20 px, текст 15–16 px, вспомогательные подписи 12–13 px; табличные цифры для чисел. Только тёмная тема. Цвет никогда не несёт смысл в одиночку.

## 12. Доступность и адаптив

Ширины 360, 390, 768, 1440 px; цели нажатия от 44 px; видимый фокус; полный обход клавиатурой; диалоги удерживают фокус и возвращают его в исходную кнопку, Escape закрывает безопасно; ошибки связаны с полями и понятны без цвета; увеличение до 200 %; длинные русские имена не обрезаются; горизонтальной прокрутки нет; `prefers-reduced-motion` отключает переходы.

## 13. Критерии приёмки

1. Все проверки R2 v1 продолжают проходить: owner-only вход, отказ чужому ID, отказ прямому URL, гейтинг по окружению, security-заголовки, отсутствие утечек.
2. Новая навигация и все экраны доступны с клавиатуры на 360/390/768/1440, в тёмной теме, без переполнения.
3. Обзор, список людей, карточка, действующие доступы и история показывают реальные данные staging; недоступное честно помечено.
4. Выдача, продление и отзыв работают на staging через панель, пишут журнал с причиной и исполнителем, не срабатывают дважды при повторе запроса и корректно отказывают при конфликте.
5. Полный `pytest` на итоговом снимке кода; браузерная проверка сценария владельца; скриншоты; запись фактов в `STATUS.md` и `DECISIONS.md`.
6. Нативные iOS/Android проверки отмечаются как непроверенные, если устройств нет.
