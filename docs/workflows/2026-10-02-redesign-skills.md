1. mobile-app-ui-design — композиция мобильных экранов, взаимодействие и главный порядок решений.
2. apple-liquid-glass — дополнительный визуальный язык: цельные поверхности, списки с разделителями, сдержанная типографика, лёгкое оформление. Не отдельный второй дизайн.

4. Expo — применимые мобильные принципы переходов, состояний загрузки, ошибок и сохранения ввода. Реализация остаётся HTML/CSS/JavaScript внутри Telegram.
5. impeccable — целевая проверка/полировка утверждённого результата, не смена выбранной композиции.
6. playwright-skill / web-design-guidelines — поведение, доступность и изображения реальных экранов. stop-slop — только понятные тексты.

## Обязательные разрешения конфликтов
Приоритет: решения владельца и безопасность → согласованный проектный дизайн → Telegram API/платформа → роли выше → общие примеры.
Mobile skill содержит крупные отступы 80–96px, glow/sparkles и React/Tailwind примеры: НЕ переносить их механически в компактное приложение. Никаких конфетти, необязательных заставок или нового стека ради навыка.
Apple app.md содержит рамку телефона, часы, Dynamic Island и постоянные 59/34px: только демонстрационные иллюстрации. В рабочий Mini App НЕ переносить; использовать реальные safe areas Telegram и устройства, не рисовать вторую системную панель.
Apple tokens.css не подключать поверх существующей темы целиком: переносить выбранные значения в одну согласованную систему. Стекло необязательно; только ограниченный эффект на перекрывающих слоях, с непрозрачным доступным вариантом. Обычный контент без blur.
Expo native компоненты, Expo Go, EAS, SecureStore и маршруты React Native неприменимы буквально к текущему веб-стеку. Не запускать эти команды, не отправлять исходники/логи через submit-expo-feedback, не устанавливать дополнительные sibling навыки по цепочке без причины.
Шрифты — системные с кириллицей либо уже лицензированные в проекте. Не скачивать и не раздавать файлы Apple. Нечитаемый мелкий/бледный текст и потерянные функции не оправдываются словом premium.
Примеры с выдуманными метриками/состояниями разрешены только в явно подписанном макете. В рабочем интерфейсе показывать реальные данные, состояние оплаты и ошибки.
Сначала варианты трёх ключевых экранов и выбор владельца; затем согласование дизайна/плана и реализация. Новые инструкции не означают, что старые навыки доказанно вызвали плохой результат.
