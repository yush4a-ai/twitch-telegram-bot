# Production release — TwitchSignalBot

Один осознанный шаг вместо ручной процедуры. Скрипт ничего не отправляет
пользователям и не меняет данные приложения: он только читает сервер, загружает
код и проверяет результат.

## Одна команда

```powershell
# 1. Сначала «примерка»: пакет и свежая копия базы, без выкладки
.venv\Scripts\python.exe -m scripts.production_release --commit HEAD --dry-run

# 2. Сама выкладка (нужно явное --yes)
.venv\Scripts\python.exe -m scripts.production_release --commit <sha> --yes
```

Полезные флаги:

- `--allow-dirty-runtime` — если в дереве есть незакоммиченные правки runtime-файлов,
  но выкладывать нужно именно указанный коммит (в пакет всегда идут только
  зафиксированные Git-объекты);
- `--skip-backup` — пропустить снятие копии базы (не рекомендуется).

## Что скрипт делает по шагам

1. Пинит цель: проект `14282646…`, окружение `production`, сервис `worker`,
   диск `9afd2204…`, публичный адрес и ожидаемое имя бота `@TwitchSignalBot`.
2. Проверяет, что коммит существует и является предком `HEAD`.
3. Собирает runtime-пакет **только из зафиксированных Git-объектов**
   (`scripts/runtime_package_manifest.py`), проверяет наличие ключевых файлов.
4. Снимает **согласованную** копию базы через SQLite backup API на сервере и
   проверяет `integrity`, внешние ключи, число каналов и миграций. Обычное
   скачивание файла использовать нельзя: оно даёт несогласованную копию.
5. Загружает пакет изнутри его каталога (загрузка с указанием пути собирает не
   тот каталог и падает — проверено 04.10.2026).
6. Ждёт `SUCCESS` и проверяет: `/healthz`, `/app`, `/admin` = 200;
   `/admin/api/snapshot`, `/streamer/api/profile` = 401; юридические страницы = 503;
   `getMe` = `@TwitchSignalBot`; в журнале нет `TwitchAuthError` и `ConfigError`.
7. Сверяет **фактический артефакт**: каждый файл в контейнере сравнивается с
   собранным пакетом по SHA256. Успешный деплой сам по себе не доказывает, что в
   `/app` лежит именно собранный пакет. Проверка на живом контуре 04.10.2026:
   165 файлов, расхождений 0.

Любой сбой останавливает релиз: предыдущий рабочий деплой остаётся активным.

## Тестовый контур

**Staging выключен владельцем 05.10.2026 и не является обязательным шагом.**
Проверка идёт локально на финальном снимке, затем релиз в рабочий контур.

Скрипт всё ещё умеет работать с тестовым контуром
(`--environment staging`), если владелец когда-нибудь вернёт его: копия базы
забирается через ssh, имя бота там не пинится и журнал не сканируется. Отдельный
workflow авто-деплоя тестового контура удалён вместе с выключением окружения.

## Откат

- Код: в Railway переразвернуть предыдущий успешный деплой (его ID печатает
  `railway deployment list --environment production`), либо выложить предыдущий
  коммит тем же скриптом.
- Данные: копия, снятая перед выкладкой, лежит в `.release/backups/`; в Railway
  она же остаётся в `/data/backups/`. Подписки, отключённые как недоступные,
  восстанавливаются включением уведомлений — строки не удаляются.

## Что важно помнить

- **Автодеплой Railway держим выключенным** для обоих окружений. Он был
  включён на production и означал, что любой push в `main` уезжает живым людям.
- `main` синхронизирован с выложенным кодом; релиз помечается тегом
  `released-production-<дата>`. Старая линия сохранена ветвями `archive/*`.
- GitHub Actions (`.github/workflows/tests.yml`) прогоняют тесты на каждый push.
  Файл workflow в `main` появится, когда у токена будет scope `workflow`.
- Защита ветки `main` (запрет force-push и удаления) настраивается владельцем в
  GitHub: Settings → Branches.
