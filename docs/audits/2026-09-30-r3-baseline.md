# R3 — локальная синтетическая опора перед изменением данных и fan-out

Дата: 2026-09-30. Исходный код до изменения схемы/очереди: `d979a58` (R2 staging-пакет); нагрузочный инструмент — `scripts/load_harness.py`. Полные машинные результаты: `docs/audits/2026-09-30-r3-baseline.json`.

## Метод

Windows, Python 3.12.10, SQLite 3.49.1, одна `Database`/`aiosqlite.Connection` и текущие методы `add_channel`, `snapshot_tracked_state`, `add_stream_sample`, `get_stream_samples`. Seed `20260930`, один sample на назначение, 100 synthetic destinations на один Twitch login, новая временная DB для каждого профиля. Никаких Telegram/Twitch запросов, пользовательских ID, production/staging DB или реальных сообщений. Инструмент отказывает при существующем DB path и пути вне OS TEMP.

| 10 000 / 100 | 10 000 | 93.76 с | 1.88 / 7.09 / 12.01 мс | 386 строк/с | 18.77 мс | 3.61 MiB / 3.95 MiB | 39.0 MiB |

Один Twitch snapshot становится 100 записями `stream_samples`, поскольку старый writer выполняется для каждого destination. Это **100-кратный множитель числа sample rows в данном профиле**, не утверждение о 100-кратном размере всей БД. При двух предварительных прогонах того же 10k профиля время было примерно 42.15 и 38.80 с, а sample p95 — 4.24 и 2.26 мс; третий прогон выше заметно медленнее. Локальная Windows/disk нагрузка делает latency нестабильной, поэтому один p95 не годится как production SLA или порог PostgreSQL.

Измерение не включает Telegram rate limits, Twitch HTTP, preview render, реальные 20–40k профили, параллельные readers/writers, Railway Volume latency и восстановление после restart. Оно подтверждает конкретный источник лишних записей и даёт исходный тест для сравнения после общей таблицы observations и durable queue. Решение о PostgreSQL не принято.
