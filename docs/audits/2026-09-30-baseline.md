## Runtime и доставка

`main.py:430-642` начинает с БД, инвалидирует неполные после restart метрики, поднимает OAuth HTTP server, EventSub, preview, poller и Telegram long polling. Завершение любого из основных фоновых task приводит к перезапуску внешним циклом `run_forever()` (`main.py:646-663`); во время shutdown health provider снимается до закрытия ресурсов. Отдельного распределённого leader lock нет; код и README предполагают один instance.

`StreamPoller._check_once()` (`bot/poller.py:596-630`) выполняет восемь стадий **последовательно**. Ошибки одной стадии собираются, остальные стадии всё равно исполняются, но длительная операция удлиняет весь цикл. В `_check_streams()` (`bot/poller.py:837-1241`) Twitch live streams запрашиваются пакетно, а затем для каждой пары login/chat идут await на Telegram и БД. `run()` (`poller.py:505-543`) спит полный интервал после завершения цикла, поэтому реальный период равен duration + interval. `TelegramRetryAfter` обрабатывается локально с общим бюджетом ожидания 2 с за цикл (`poller.py:460-503`), но durable queue для live notifications пока нет.

Live-post переходы имеют durable состояние (`tracked_channels.last_message_kind`, `media_transition_pending`, `media_transition_target_kind`; `bot/database.py:165-196`), conditional DB updates и тесты crash/retry. Отчётный outbox хранит payload и статусы частей (`bot/database.py:282-309`), а `recover_finished_sessions()` запускается первой стадией цикла. Это сильнее, чем утверждение «все уведомления теряются при restart»: такое утверждение не подтверждено. Проверка доставки в живой staging-чат в R0 не выполнялась.

## Данные и рост

В `SCHEMA` (`bot/database.py:165-428`) 22 таблицы (`rg -c 'CREATE TABLE IF NOT EXISTS' bot/database.py`). `tracked_channels` — одновременно subscription и per-destination live state; `stream_samples` и `stream_history` содержат `chat_id`, `twitch_login`, `stream_id`, то есть общий Twitch-снимок повторяется для разных получателей (`database.py:237-276`; запись `poller.py:1173-1186`). `stream_chatters`, напротив, хранится один раз на физический stream (`database.py:340-350`). `report_deliveries` — отдельный durable outbox только итоговых отчётов. Retention raw report data — 24 часа после завершения stream (`poller.py:112,621-626`, `database.py:2322-2404`); audit/financial event store отсутствует.

Миграция на startup начинается `BEGIN IMMEDIATE` (`database.py:477-490`) и добавляет недостающие колонки (`database.py:490-675`). Отдельного versioned migration ledger нет. Код включает WAL, требует его для файловой DB и проверяет путь/permissions. В репозитории нет исполняемого SQLite online backup/restore runbook или drill; README лишь требует backup. Размеры/задержки реальных БД, integrity и восстановление не проверялись, потому что R0 не копирует production DB.

Preview имеет отдельные ограничения: `CaptureService` допускает до двух активных захватов (`bot/preview_capture/service.py:46,737-759`), а `PreviewManager` ограничивает тяжёлые artifact jobs семафором, по умолчанию одним (`bot/config.py:13-16`, `bot/preview_runtime.py:227`). Один artifact затем отправляется получателям **последовательно**, с reuse Telegram `file_id` после первой успешной отправки (`preview_runtime.py:841-897`). Это ограничивает пиковую работу, но latency на большой fan-out не измерена. `/healthz` намеренно не включает preview; отдельный preview snapshot есть у poller/owner `/health` (`poller.py:410-441`, `oauth.py:97-159`).

## Документы и безопасность

До R0 README и `.env.example` описывали preview как P3 no-op/P4A не подключённый, хотя `main.py:184-286` собирает реальный provider при `PREVIEW_RUNTIME_ENABLED=true`; оба Railway environment имеют `true`. README также предписывал draining ≥30 с, тогда как в active deployment metadata он `null`; это требование, а не подтверждённый факт. Точные исправления внесены в R0 без изменения продукта.

`OWNER_CHAT_ID` проверяется для Telegram admin-команд; отдельного owner web auth/API нет. OAuth state создаётся случайно и сверяется с pending map (`bot/oauth.py:217-242,311-323`), токены шифруются Fernet (`bot/database.py:432-440,596-640`), `mask_chat_id` применяется к operational logs (`bot/logging_utils.py`, `bot/poller.py:460-503`). Проверка всех потенциальных PII payload в логах не выполнена и остаётся задачей перед аналитикой/платежами. Deep-link payload для добавления Twitch-канала валидируется (`bot/deep_links.py:10-49`, `handlers/streams.py:446-548`). Mini App init data validation, entitlement, order/payment, referral attribution, financial audit log и публичный сайт в текущей структуре отсутствуют.

## Неизвестное и следующий этап

- Реальные latency/CPU/RAM/disk, размер и integrity обеих SQLite DB, backup/restore RPO/RTO, Telegram throughput и нагрузка 20–40 тыс. не измерены. R9 должен поставить пределы на основе синтетических профилей.
- Строки секретов не сравнивались; соответствие staging токена именно `@TwitchSignalTestbot` пока подтверждается только заявленным назначением, не вызовом Telegram `getMe`.
- Содержимое активного staging deployment не привязано в Railway metadata к Git SHA; перед дальнейшим deploy нужна воспроизводимая маркировка build/commit.
- Не выполнены staging Telegram E2E и ручная приёмка preview в R0; это отдельный gate R1/R6.
- Не подтверждены политика auto deploy и rollback процедура production вне свидетельства текущего `main` deployment. В R1 надо закрепить безопасный staging deploy, healthcheck, data/secret isolation и backup/rollback drill без действий с production DB.

Следующий самостоятельный этап — **R1 Safe Development/Staging Workflow**. До его завершения допустимы локальные feature commits в `autonomous/twitchsignal-roadmap`; push `main` и любые production действия исключены.
