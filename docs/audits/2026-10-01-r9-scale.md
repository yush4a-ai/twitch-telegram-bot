# R9 synthetic scale validation: локальный и staging аудит

Дата: 2026-10-01. Исходные результаты лежат рядом: `2026-10-01-r9-local-{20k,30k,40k}.json` и `2026-10-01-r9-staging-{20k,30k,40k}.json`. Для каждого размера и среды выполнен один прогон. Локально: Windows, Python 3.12.10, SQLite 3.49.1; на Railway: pinned staging с `TwitchSignalTestbot`.

## Сценарий и сохранность

Harness создавал новую временную SQLite DB для каждого размера: 100 фиктивных назначений на логин и два poll-like раунда. Каждый раунд записывал один shared observation на логин; durable live job оставался одним на назначение с revision 2. После повторного открытия DB harness возвращал просроченную lease и отвергал старый ack. Fake sender без сети читал актуальный sample и завершал все jobs. Отдельная восстановленная копия прошла `integrity_check=ok`, 39 таблиц. Все шесть прогонов закончили с pending/leased/failed = 0. Workload не открывал активную staging DB.

Свободное место на временном диске после профилей: 232,5–232,8 GB. Ни один профиль не достиг ограничения 256 MiB RSS, 15 минут или 512 MiB свободного диска.

30k drain оказался медленнее относительно объёма, чем 20k и 40k. Причина не установлена; один прогон на размер и фоновая нагрузка Windows не позволяют назвать это устойчивым свойством SQLite. 40k не продолжил пропорциональный рост 30k, поэтому автоматическое решение о смене DB engine по этим данным было бы преждевременным. R3 shared-only результаты измеряли другой, более узкий путь и не являются прямым performance baseline.

При условном глобальном интервале стартов Telegram 40 ms нижняя арифметическая граница для 20k/30k/40k — 800/1200/1600 s, без сети, ошибок и иных отправок. Fake sender в этом прогоне имеет нулевой сетевой интервал. Он проверяет очередь и DB, но не подтверждает время доставки через Telegram.

## Отдельные пробы

Локальная preview probe: coordinator при лимитах 1/2/4 завершил 4/4 задач, максимум одновременно захваченных равен каждому лимиту. Синтетический FFmpeg сформировал 24 s, 854×480, 30 fps, H.264 MP4 без аудио, 3 244 466 B; encode wall 2,87 s, CPU 2,218 s. Windows FFmpeg не выдал `maxrss`, поэтому значение не подставлено. Это не Twitch capture и не загрузка видео в Telegram; существующий 6→12→18→24 pipeline не менялся.

Mock billing probe: 100 конкурентных повторов verified capture дали один payment и один grant; плохая подпись отвергнута, refund отозвал grant, повтор refund не создал новый event; cancel и expiry завершили по одному pending order. Всё выполнено в `:memory:` DB, без настоящих платежей.

Все stage прогоны подтвердили revision 2, возврат lease, отклонение stale ack, `integrity=ok` и восстановление временной DB. Peak process RSS остался ниже 256 MiB; 15-минутный лимит не сработал. Показатель свободного места `/tmp` составил около 1,995 TB на host filesystem. Он не измеряет квоту Railway Volume, поэтому по нему нельзя делать вывод о запасе `/data`.

Stage preview coordinator завершил 4/4 задач при лимитах 1/2/4, максимум одновременных captures равен лимиту. FFmpeg создал 24 s, 854×480, 30 fps, H.264 MP4 без аудио размером 3 244 463 B; encode wall 2,255 s, CPU 2,689 s. FFmpeg `-benchmark` не сообщил `maxrss`; отдельный такой же запуск через `resource.RUSAGE_CHILDREN` показал 172 240 896 B максимального RSS дочернего процесса. Это два разных запуска, а не общий замер одного encode. Stage mock billing повторил локальные инварианты: 100 replay, один payment/grant, revoke после refund, плохая подпись отклонена, cancel/expiry по одному, `integrity=ok`.

После прогона активная staging DB сохранила `integrity=ok` и 39 таблиц; growth attributions/referral codes и billing orders остались 0. Число её обычных `notification_jobs` изменилось с 1 до 3, все три `done`. Staging bot работал во время synthetic профилей; без анализа содержимого job источник двух новых записей не установлен. Synthetic workload открывал только новую DB в `/tmp`, поэтому свои 20k/30k/40k jobs в активную DB не писал. `/site` вернул 200 с `X-Robots-Tag: noindex, nofollow`, а анонимный `/admin/api/snapshot` вернул 401.

## Решение и границы

R9 принят как инженерная synthetic-проверка на staging. Пока сохраняем SQLite с одной replica и durable queue: stage DB read p95 составил 3,25/3,52/3,48 ms, запись observation p95 1,09/1,25/1,35 ms; все jobs завершились без потерь и ресурсного stop. По этим измерениям мы не меняем DB engine. Следующим нужно измерить настоящий Telegram start budget, сетевые задержки, совместную нагрузку остальных send путей и poller при живых Twitch событиях. Теоретический 40 ms интервал даёт минимум 800/1200/1600 s для 20k/30k/40k стартов; fake sender его не применял.

Мы не проверяли реальную доставку 20–40k в Telegram, Twitch capture под сетью, горизонтальное масштабирование Volume, real owner Login/Mini App/Streamer journey или production. Одна серия на размер не задаёт SLA и не описывает разброс. R8 сайт остаётся неиндексируемым, реальных платежей и provider выбора не было. Для публичного запуска нужны отдельные решения владельца по домену/названию, правовым ограничениям, провайдеру и реальному account E2E; staging работа на этом завершена без production изменений.
