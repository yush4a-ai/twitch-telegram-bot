# R9 synthetic scale validation — промежуточный аудит

Дата: 2026-10-01. Исходные локальные результаты: `2026-10-01-r9-local-20k.json`, `2026-10-01-r9-local-30k.json`, `2026-10-01-r9-local-40k.json` рядом с этим файлом. Один прогон каждого размера на Windows, Python 3.12.10, SQLite 3.49.1. Staging-проверка и полный suite ещё не завершены.

## Сценарий и сохранность

Для каждого размера новая временная SQLite DB, 100 синтетических назначений на один логин, два poll-like раунда. Shared observation записывался один раз на логин за раунд; durable live job оставался одним на назначение с revision 2. После повторного открытия DB просроченная lease была получена вновь, старый ack отвергнут. Fake sender без сети прочитал актуальный sample, завершил все jobs, после чего snapshot восстановлен в отдельную DB. В каждом прогоне `integrity_check=ok`, восстановленная копия `ok`, 39 таблиц, pending/leased/failed = 0. Активные пользовательские DB не открывались.

Свободное место на временном диске после профилей: 232,5–232,8 GB. Ни один профиль не достиг ограничения 256 MiB RSS, 15 минут или 512 MiB свободного диска.

## Задержки

Ниже p50 / p95 / p99 в миллисекундах. Observation — одна DB-запись для логина; DB read — чтение текущего sample fake sender; очередь — от начала первой постановки до fake send. Snapshot tracked и `request_live_updates` имеют лишь два замера, по одному на раунд; их p95 нельзя считать устойчивым процентилем.

30k drain оказался медленнее относительно объёма, чем 20k и 40k. Причина не установлена; один прогон на размер и фоновая нагрузка Windows не позволяют назвать это устойчивым свойством SQLite. 40k не продолжил пропорциональный рост 30k, поэтому автоматическое решение о смене DB engine по этим данным было бы преждевременным. R3 shared-only результаты измеряли другой, более узкий путь и не являются прямым performance baseline.

При условном глобальном интервале стартов Telegram 40 ms нижняя арифметическая граница для 20k/30k/40k — 800/1200/1600 s, без сети, ошибок и иных отправок. Fake sender в этом прогоне имеет нулевой сетевой интервал. Он проверяет очередь и DB, но не подтверждает время доставки через Telegram.

## Отдельные пробы

Локальная preview probe: coordinator при лимитах 1/2/4 завершил 4/4 задач, максимум одновременно захваченных равен каждому лимиту. Синтетический FFmpeg сформировал 24 s, 854×480, 30 fps, H.264 MP4 без аудио, 3 244 466 B; encode wall 2,87 s, CPU 2,218 s. Windows FFmpeg не выдал `maxrss`, поэтому значение не подставлено. Это не Twitch capture и не загрузка видео в Telegram; существующий 6→12→18→24 pipeline не менялся.

Mock billing probe: 100 конкурентных повторов verified capture дали один payment и один grant; плохая подпись отвергнута, refund отозвал grant, повтор refund не создал новый event; cancel и expiry завершили по одному pending order. Всё выполнено в `:memory:` DB, без настоящих платежей.

## Следующий checkpoint

Полный suite и review финального кода, pinned staging check, новый consistent online backup активной staging DB с внешним восстановлением. Затем deploy только на staging, bot identity, временные профили 20k/30k/40k с resource stop, preview/billing probes, повторная проверка активной DB и production deployment identity. До этих шагов R9 не принят на staging.
