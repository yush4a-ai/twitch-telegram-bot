## Подтверждённые механизмы

| Назначение | Факт из документации | Источник |
|---|---|---|

| Выбор у провайдера | `POST /v2/transaction/process`; ответ использует `url`, а не `redirect` | [Hosted выбор](https://docs.platega.io/создание-платежной-ссылки-без-заданного-метода-33845703e0) |
| Статус | `GET /transaction/{id}`; проверять ID, статус, сумму, валюту, merchant и метод | [Статус платежа](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0) |

| Связь без платежа | `GET /balance/all` — кандидат для будущей проверки credentials без создания транзакции | [Балансы](https://docs.platega.io/получение-балансов-33582950e0) |

В запросе создания предусмотрены server-generated `orderId` и `payload`, а также `metadata.userId/userName`; поле `id` не отправляется как новый transaction ID. Обязательность metadata для нашей категории нужно подтвердить у менеджера. В опубликованной схеме metadata оба поля помечены обязательными внутри объекта; отсутствие имени пользователя требует согласованного формата, а не фиктивного antifraud. Клиентские ID и display name не являются проверкой покупателя.

## Callback

Провайдер отправляет POST на наш публичный HTTPS endpoint с доверенным сертификатом, заголовками `X-MerchantId`/`X-Secret` и JSON. Описание перечисляет CONFIRMED, CANCELED, CHARGEBACKED. Указаны ожидание ответа до 60 секунд и до трёх повторов через пять минут. Event ID, timestamp и подпись тела обычного callback не описаны. [Официальный callback](https://docs.platega.io/callback-об-изменении-статуса-транзакции-29209725e0).

Наше решение для согласования: строгие заголовки/JSON, сравнение credentials без зависимости времени от совпадения, ограниченный inbox и проверка transaction через GET перед выдачей доступа. Нормализованное повторное событие не продлевает grant. Не переносить HMAC mock-провайдера или отдельного Payout API на обычные callbacks.

## Расхождения и ограничения

- Callback description содержит CHARGEBACKED, но enum в его request schema ограничен CONFIRMED/CANCELED. Общая PaymentStatus включает CHARGEBACKED. Формат и семантику возврата/chargeback подтвердить у менеджера; неизвестные значения не дают доступ.
- В TransactionStatusResponse поле merchant записано `mechantId`. Критические поля не все отмечены required. Адаптер должен требовать доказуемое совпадение merchant/ID/денег; ответ без этих данных не подтверждает оплату.
- Для POST создания не найдена гарантия идемпотентности или официальный GET по нашему orderId. Нельзя автоматически повторять POST после неопределённого тайм-аута. Уточнить механизм поиска/восстановления у менеджера.
- `accepted` на отмену не доказывает завершённый возврат. Нужны окончательный статус и отдельный учёт ручного контроля. Частичный возврат и гарантия идемпотентности этого POST не документированы.
- Не использовать `/cancel` как безусловное действие кнопки «Закрыть оплату»: endpoint может возвращать деньги. Закрытие UI, отмена неоплаченного заказа и возврат оплаченного различаются.
- Recurring СБП использует метод 6 и отдельный subscription lifecycle. Он прочитан, но исключён из текущего продукта без автосписаний. Значение «месяц=30 дней» в recurring schema не определяет наш разовый период.
- Payout/card storage имеют другой HMAC и операции выплат. Они не нужны покупателю Plus; карты, выводы, ERIP, криптовалюта, H2H и массовые экспорты в интеграцию не входят.

## Площадка продажи

Telegram требует Stars для цифрового доступа, продаваемого внутри бота/Mini App, включая продавцов с отдельным сайтом. Поэтому запрошенный рабочий выбор «Stars / СБП / карта» внутри Mini App конфликтует с платформенным требованием. Предложение spec: Stars внутри Telegram, Platega для отдельно согласованного самостоятельного сайта; не делать ссылку обхода кассы в Mini App. [Telegram Digital Goods](https://core.telegram.org/bots/payments-stars), [условия §6.2](https://telegram.org/tos/bot-developers).

## Самозанятый и НПД

[Platega позиционирует работу с самозанятыми без ИП](https://platega.io/ru/blog/cheklist_samozanat). Это не подтверждение допуска нашего магазина, подключения конкретных методов, бесплатного sandbox или автоматических чеков. Прочитана доступная [страница оферты](https://platega.io/ru/public-offer), но действующий договор в выдаче отсутствует. Старый `admin.platega.io/offer` перенаправляет на недоступный через инструмент `partners.platega.io/offer`; текст договора владельца не получен.

ФНС описывает формирование/передачу чеков через «Мой налог» и отдельные условия работы через посредника. Кто выполняет это в конкретной схеме Platega, определяется подтверждённой схемой расчётов и договором. Наша запись платежа не заменяет налоговый чек. [ФНС: вопросы НПД](https://npd.nalog.ru/faq/?from=index), [кабинет «Мой налог»](https://npd.nalog.ru/web-app/).

От владельца после регистрации нужны несекретные ответы менеджера: допуск цифрового Plus и статуса самозанятого; методы 2/11 и RUB для 150/200 ₽; требуемая metadata; безопасный тестовый режим; договор/ответственность за чек и возвраты; формат CHARGEBACKED/merchant; идемпотентность создания/возврата и восстановление неизвестной транзакции. Никаких обращений менеджеру от имени владельца не отправлено.
